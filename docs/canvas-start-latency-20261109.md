# 画布手势起始延迟修复（2026-11-09）

> 本文记录前一轮诊断与修复。后续已移除自动位图快照和运动显隐替换，并恢复纯 rAF 绘制调度；当前实现及验证见 `canvas-live-render-20261109.md`。下文的快照调度和 24ms 兜底不再是当前方案。

问题：进入项目后，拖动画布或滚轮缩放在起始阶段停顿，随后才跟随输入。

本次定位到的是输入期间的同步样式计算、预览显隐和快照调度叠加，不能归结为“所有页面同步重排 100～300ms”。项目 182 的样本有 72 个画板块，当前只挂载了 2 个原型 iframe。一次原始 6 手势对照中，布局计算累计约 2ms，样式重算累计约 269ms。

## 修改

- `canvasMotion.ts`：包括首样本在内的变换写入统一合并到帧调度；输入状态仍即时累计，释放手势时刷新最后一个样本，聚焦和销毁会取消旧任务。
- `PrototypeView.vue`：在挂载、尺寸变化及窗口滚动时测量视口位置，普通滚轮起始使用缓存。iframe 内的输入通过已绘制的相机与画板坐标投影，不读取布局；CSS 聚焦动画和临时目标高亮缩放期间保留 DOM 测量兜底。投影使用已绘制位置，避免将尚未绘制的逻辑输入误用于命中坐标。
- `PrototypeView.vue` / `PageCanvas.vue`：快照和占位保持绝对定位布局，通过透明度切换；真实 iframe 不卸载。没有对每个画板添加 `will-change`。
- `canvasSnapshot.ts`：监听手势开始和结束，取消待执行的空闲任务；手势结束后保留 300ms 安静期。跨越手势的旧任务不能发布快照，资源完成后会检查取消状态，跳过大 CSS 字符串复制、后续序列化和位图绘制。
- 平移开始时不再用新的空 Set 重复清空本来为空的连线选择。

`Image.decode()` 本身没有可用的 AbortSignal。本次采用阶段检查和废弃过期结果，保留共享下载缓存，没有声称能抢占正在执行的解码、DOM 克隆或其它同步任务。

## 验证

- 前端 198 项测试通过，覆盖首帧合并、结束刷新、过期调度取消、滚轮锚点、iframe 输入投影、快照安静期及任务失效；原有编辑、权限、保存、连线、导航和撤销回归一并通过。
- TypeScript 检查和生产构建通过。
- ego-browser 在真实项目中进行只读性能诊断，并在内存适配器隔离的工作台中验证：创建空白画板、添加按钮、画布平移/缩放后选择和拖动元素、修改文字与尺寸、绘制和调整矩形、撤销/重做、设计与交互模式切换。测试写入只发生在项目 900001 的内存适配器中。
- 平移/缩放后的原始文档与元素节点保持相同；撤销/重做可能按原有逻辑恢复历史文档，不以保留节点身份为要求。

## 测量范围

在相同项目、72 个画板块和 2 个活跃 iframe 的对照中，6 次合成滚轮起始事件的同步处理耗时如下（毫秒）：

| 对照 | 6 次处理耗时 |
| --- | --- |
| 修改前 | 1.0、49.2、39.2、39.8、23.7、32.6 |
| 首轮修改后 | 3.8、0.1、0.5、0.4、0.5、0.3 |

该测量发生在补充 iframe 坐标投影之前，反映主视口输入处理减少了强制计算；不等同于输入到屏幕显示的总延迟。浏览器自动化窗口状态会影响帧调度，不能用此样本承诺 0ms 卡顿或稳定 60/120fps。iframe 坐标投影另以不读取布局、保留已绘制锚点的回归测试验证。
